# SoleThief commerce implementation: source of truth

This execution plan supersedes the phase ordering in the pre-existing gap analysis without replacing that document or its uncommitted work. Stages 1 and 2 are implemented locally. Stage 2 adds catalog browsing and a persistent demonstration bag, not checkout, authentication, admin, or real stock promises. Existing fonts, ivory/indigo identity, fixed four-shoe hero and GSAP/Matter interactions are preserved.

## Phased delivery and acceptance gates

1. **Foundation (completed locally):** public Supabase configuration, lazy client, explicit preview catalog adapter, individual-pair schema, deny-by-default commerce writes, faithful seed, setup documentation and focused tests. Gate: build/lint/tests; remote migration/RLS acceptance remains blocked on infrastructure/credentials.
2. **Catalog/cart:** adopt the adapter in existing visual components without redesign; preserve numeric product routes and hero physics; explicit loading/error/preview states; persistent versioned cart of product IDs only (quantity one per pair), stock-aware server reads, filtering. Never treat cached price/availability as authoritative. Gate: unchanged visual regression snapshots, cart persistence and missing/sold product tests.
3. **Auth/customer:** Supabase sign-in/out/session recovery and verified redirect allowlist, customer-owned profile/address forms, private account/order history. Profiles are explicitly inserted after authentication; there is no signup trigger. Define email confirmation and PKCE callback handling before enabling it (URL detection is currently disabled). Gate: two-user isolation, session expiry and address ownership tests.
4. **Secure checkout/orders/payments:** trusted Edge Functions plus transactional database functions; provisional Razorpay for India/INR, not configured. Reprice and validate cart/address server-side; reserve pairs and snapshot orders atomically; create provider orders; verify captured payments/webhooks; expire reservations and reconcile failures. Gate: concurrency, idempotency, tampering, webhook replay, late payment and refund tests before enabling purchases.
5. **Admin/operations:** server-authorized admin access using private admin_roles, inventory verification, catalog/image management, fulfillment/refunds, append-only audit trails, webhook event ledger, stock/payment reconciliation, monitored expiry jobs. Gate: no self-escalation; audited transitions and operator recovery runbooks.
6. **Validation/launch:** local and hosted RLS tests, full browser journeys, accessibility/mobile/visual/performance checks, Razorpay test-mode acceptance, production domain/auth/CORS configuration, backups and recovery, secret rotation, observability, rate limits and release checklist. Gate: reviewed deployment with actual credentials, verified physical stock and merchant approval.

## Stable contracts for subsequent tasks

- `src/lib/supabase.js`: `readSupabaseConfig(env)`, `initializeSupabase(env, factory)` and lazy `getSupabaseRuntime()`. Runtime is `{client, status, message}`; statuses are missing/invalid/configured. Configured means syntactically accepted, not reachable or authenticated. A missing/invalid client is null, not an import-time exception. Only publishable or legacy anon keys are accepted; this guard cannot make a mistakenly bundled secret safe. Never set secrets in Vite environments.
- `src/services/catalog.js`: `catalogService.list({allowPreview: false})` resolves `{source: 'preview' | 'supabase', checkoutEnabled: false, products}`. Explicit `allowPreview: true` permits fallback ONLY when both public credentials are absent. Partial/invalid config, network/RLS/query errors and malformed responses throw; empty live catalog stays empty. Preview is not an order simulator.
- Product adapter preserves `id`, `name`, `brand`, display `price`, `size`, `frontImage`, `sideImage`, and local physics by matching ID; adds integer `priceMinor` and `currency: 'INR'`. Arithmetic must use minor units, never formatted price strings. Images remain existing public assets, not an invented Storage bucket. Live metadata is public and must not include supplier/private information.
- Stage 2 wires the service into Shop, product routes, Cart and the homepage shopping grid. The homepage hero still uses exactly the four static presentation objects; the independent shopping grid shows at most four adapter products. Supplying credentials changes catalog data, never enables checkout. Invalid/live errors are explicit and never become preview.
- `products`: positive integer IDs, one individually photographed pair per row. IDs 1-4 map exactly to current routes; pairs 3 and 4 remain separate despite sharing a name. New IDs must be allocated by trusted tooling (no identity sequence yet). INR integer paise: 1900000, 1850000, 1650000, 1650000.
- `inventory_pairs`: one row per product; unavailable/available/reserved/sold state, associated order, reservation deadline. Seed uses unavailable because static display is not proof of stock. Private to service role; later availability endpoint must not expose reservation owners.
- `profiles` and `addresses`: tied directly to auth.users. Customers can insert/read/update only their own allowed fields; delete their own addresses. No client-writable roles or ownership changes. Address country is IN and postal code is six digits; full shipping validation is still required server-side.
- `orders`: customer UUID, status, INR totals in integer paise, immutable shipping snapshot, per-user UUID idempotency key, unique Razorpay order/payment IDs and expiry. Customer read-only. No hard customer deletion with retained orders; define retention/anonymization policy later.
- `order_items`: historical name/brand/size/image/price snapshot, quantity fixed at one, generated line total, unique pair per order. Customers read only through parent ownership, including when a product becomes inactive. Repeated product across cancelled/expired historical orders is permitted.
- `admin_roles`: no browser reads/writes, not sourced from user-editable auth metadata. Operator provisioning via trusted SQL only; later Edge Functions verify JWT identity and query role server-side on every privileged request. A service-role key bypasses RLS and must never be shipped to clients.
- All seven tables enable RLS and explicit grants. Public reads only active products; authenticated customers read their own orders/items. No browser insert/update/delete grants or policies for catalog, inventory, orders/items or roles. There are no privileged RPCs yet. Service role is trusted, not constrained by customer RLS.

## Required atomic/server design for stage 4 (not implemented)

1. Verify caller JWT server-side; ignore client user ID, prices, totals, payment status and inventory. Require authenticated checkout initially; guest checkout requires a separate reviewed design.
2. Validate address ownership then copy a normalized snapshot. Lock requested pair rows in deterministic product-ID order; check availability and catalog active state; derive all prices, shipping, tax and discounts server-side. Insert order/items and reserve every pair in ONE transaction or none. Persist per-user idempotency key plus a request fingerprint; same key/different payload is a conflict.
3. Enforce item sum equals order subtotal and allowed state transitions in narrowly scoped transactional functions. Current row constraints do not enforce cross-table sums or inventory/order lifecycle consistency. Revoke default PUBLIC function execution, fix search_path and grant only trusted backend invocation; never expose generic service-role writes to browsers.
4. Provider API calls cannot participate in the database transaction. Use pending states/outbox/retry and reconciliation around Razorpay order creation; attach unique provider IDs server-side. Do not free a reservation while a payment capture is unresolved without a late-payment recovery policy.
5. Verify Razorpay callback signature using server-stored provider order ID and secret; verify webhook signature against raw request bytes using the separate webhook secret. Validate provider order/customer association, amount/currency and captured status via trusted provider data. Client success callbacks alone never mark paid.
6. Add durable provider-event deduplication and payment attempt/refund records before shipping payments. Lock order and inventory rows; perform idempotent paid + sold transition together. Reservation expiry/cancel/refund processing must use the same locking/state-machine rules. Late captured payments need reconciliation/refund, never sale of an already reallocated pair.
7. Protect endpoints with schema validation, ownership checks, rate limits, limited CORS and safe logs. Add auditable operations; no secrets or address/payment PII in frontend telemetry.

## Deferred risks

Credentials, Supabase project, remote schema/RLS verification, physical stock, merchant onboarding, payment secrets, taxes/shipping/refund policy, email delivery and production domains are unavailable. Stage 1 does not establish a production checkout system. Existing `allowedHosts: true` is preserved as requested; restrict it and temporary tunnels before production. Integer minor-unit columns cap each monetary value at PostgreSQL integer range; validate limits before computation. No Storage, Realtime publication, admin UI or payment deployment is implied.

## Stage 2 handoff / 2026-10-10

- Implemented: responsive search, brand/size/INR price filters and deterministic sorting; explicit loading/error/retry/empty states; strict numeric product routes and useful missing-pair pages; accessible product links and demo Add to Bag; navbar count; remove/clear/empty bag; integer-paise subtotal with shipping/tax pending and checkout disabled. Product condition/material/authenticity claims are not invented.
- Files: src/commerce/cart.js owns storage validation and pair arithmetic; catalog.js owns filters and strict route/decimal parsing; context.js and CommerceProvider.jsx own shared catalog/cart state; CommerceUI.jsx and commerce.css supply scoped UI. Shop, Cart, Product, Navbar, ProductDetails, ProductGallery and App are integrated. Home changes only its independent featured grid, capped at four; hero physics still consumes original static data.
- Storage contract: key solethief.cart.v1; version 1, source preview or supabase, unique positive PostgreSQL integer IDs, maximum 100 pairs. No price, quantity, inventory or customer data is persisted. Missing/malformed/oversized/unknown-version storage becomes an empty bag. Extra fields are discarded; duplicate IDs collapse to one. Storage denial degrades to an in-memory bag with a visible warning. Storage events synchronize other tabs without write echoes; concurrent tabs remain last-writer-wins.
- Availability boundary: no schema or RLS changes. Public product reads cannot read private inventory. All live additions fail closed as availability unverified, including forged available/sold/reserved flags. Preview additions are demonstration-only. Source changes leave saved selections unresolved rather than silently converting preview into live stock. Missing products stay removable and suppress the complete subtotal. No checkout or order simulation is implemented.
- Catalog contract remains source/products/checkoutEnabled=false. The adapter now rejects malformed presentation fields, unsafe image schemes, duplicate IDs and out-of-range PostgreSQL integer prices/IDs. Live failures never fall back. Current catalog prices are resolved from IDs, never restored from local storage. Future checkout must independently reprice and validate stock server-side.
- Verification: 12 Node tests passed (5 foundation + 7 commerce); production build passed; lint passed with zero warnings/errors; git diff --check passed. Existing Vite returned HTTP 200 for home/shop/cart/product and transformed commerce modules. No server/tunnel process was restarted or terminated.
- Limits: Playwright, @playwright/test and Puppeteer are not installed; no browser automation or visual baseline comparison was performed. HTTP 200 is only SPA delivery, not a rendered journey. Desktop/mobile layout, keyboard/screen reader, touch/physics, denied storage and cross-tab interactions still need real-browser acceptance. No remote database, migration, RLS, stock or payment verification occurred. Build warns about a roughly 633 kB JS chunk (192 kB gzip). Live stock-aware reads remain deferred until a reviewed safe availability endpoint exists; the stage visual/browser and live-stock acceptance gates are therefore not fully satisfied.
- Next stages: retain private inventory, verify seed stock, provide safe availability without reservation-owner leakage, implement auth separately, then atomic trusted checkout/repricing/reservations/payment verification. Review shipping/tax policy, bundle splitting and the existing tooling advisory before launch. No commits or credential/configuration changes were made in stage 2.

## Stage 5 handoff / 2026-10-10

- Visual Theme: Japanese streetwear aesthetic with warm ivory (`#F1EBDD`), deep indigo (`#151B2B`), antique gold (`#C8A96E`), Anton and Cormorant Garamond typography, and 44px minimum touch targets.
